# 재사용 가능한 2D 게임 엔진 구조화 기획서

작성일: 2026-10-08  
대상: 기존 엔진을 이해하면서 개선하거나, 다른 프로젝트에서 같은 설계 원칙으로 엔진을 구축하려는 개발자  
문서 성격: 구현 전 설계 및 실행 계획. 작업 순서를 제시하며, 일정은 각 단계의 실제 범위를 확인한 뒤 산정한다.

## 1. 목적과 최종 결과

엔진의 책임, 의존 관계, 객체 수명을 명확하게 만들어 게임을 바꿔도 공통 코드를 재사용할 수 있게 한다.
개발자가 각 기능의 필요성과 호출 흐름을 설명하고, 작은 변경을 독립적으로 검증할 수 있는 구조를 목표로 한다.

최종 결과물은 다음 네 가지다.

1. 게임 코드에 의존하지 않는 엔진 라이브러리.
2. 엔진을 사용해 이동, 충돌, 씬 전환을 보여주는 작은 샘플 실행 프로그램.
3. 생성·초기화·업데이트·삭제 규칙을 설명하는 설계 문서.
4. 객체 수명과 씬 전환 등 위험한 동작을 확인하는 회귀 검증.

완료 후에는 새 게임 프로젝트가 엔진을 참조하고 자신의 씬, 행동, 리소스 목록을 등록해서 실행할 수 있어야 한다.
새 게임을 만드는 과정에서 엔진에 게임 전용 이름이나 규칙을 추가하지 않아야 한다.

## 2. 범위와 우선순위

| 구분 | 범위 | 우선순위 판단 |
|---|---|---|
| 필수 | 엔진/게임 빌드 분리, 소유권, 초기화 규칙, 씬 전환, 기본 API, 회귀 검증 | 재사용과 동작 안정성의 기반 |
| 다음 단계 | 플랫폼 의존성 격리, 입력/렌더링 접근 정리, 도구 분리 | 수정 범위를 줄이고 실행 환경을 명확히 함 |
| 필요할 때 | 물리 고정 시간 간격, 오브젝트 핸들, 직렬화, 프리팹, 리소스 핫 리로드 | 실제 사용 사례와 문제가 생겼을 때 도입 |
| 이번 범위 밖 | 3D 전환, ECS 전면 교체, 다중 렌더링 백엔드, 멀티스레드, 완성형 편집기 | 별도 목표와 검증 계획이 필요함 |

기존 그래픽 API와 오디오 라이브러리는 우선 유지한다.
폴더 분리와 프로젝트 분리를 구분한다. 기능별 폴더를 만들었다고 독립 라이브러리가 필요한 것은 아니다.
초기 빌드 단위는 Engine과 Sample 두 개를 기본으로 하고, Tools는 필요할 때 추가한다.

## 3. 설계 원칙

### 3.1 의존성은 공통 기능 방향으로 흐른다

```text
Sample 또는 Game ──→ Engine의 공개 API ──→ Engine 내부 구현
Tools ─────────────→ Engine의 공개 API

Engine 내부:
  World / Physics / Graphics / Audio / Input ──→ Core
  Windows 및 외부 라이브러리 연동 ──────────→ 내부 연동 경계

Composition Root(실행 시작점):
  창, 엔진 서비스, 게임을 생성하고 연결
```

엔진은 특정 게임의 클래스나 리소스 이름을 참조하지 않는다.
실행 시작점이 구체적인 플랫폼 구현과 게임을 선택한다.
같은 계층의 기능을 연결해야 한다면 필요한 데이터나 좁은 기능을 전달한다.
모든 기능을 조회할 수 있는 거대한 전역 객체를 기본 접근 방식으로 삼지 않는다.

### 3.2 소유권과 사용 권한을 구분한다

객체를 소유하는 곳이 생성 이후의 수명과 삭제를 책임진다.
다른 기능은 해당 객체를 사용하더라도 임의로 삭제하지 않는다.
여러 곳이 참조한다는 이유만으로 공동 소유를 도입하지 않는다.

### 3.3 상태 변경 시점을 정한다

업데이트 도중 생성, 삭제, 씬 전환 요청이 발생할 수 있다.
순회 중인 목록을 직접 변경하지 않도록 요청을 모아 정해진 경계에서 적용한다.
콜백의 호출 순서와 객체가 유효한 기간을 문서에 명시한다.

### 3.4 사용 사례로 설계를 검증한다

추상화마다 실제 사용 사례를 연결한다.
새 기능이나 인터페이스를 추가할 때는 해결하는 문제, 사용 코드, 검증 방법을 함께 작성한다.
기존 구현을 유지해도 문제가 없다면 우선 유지한다.

## 4. 기능별 책임

| 영역 | 책임 | 경계 |
|---|---|---|
| Core | 시간, 수학, 공통 타입, 로그 | 게임 규칙과 OS 창을 알지 않음 |
| Application/Runtime | 서비스 연결, 프레임 순서, 시작과 종료 | 플레이어 행동과 승패를 결정하지 않음 |
| World | 씬, 객체, 컴포넌트, 수명 관리 | 특정 게임의 생성 규칙을 포함하지 않음 |
| Input | 입력 상태와 조회 API | 플레이어 이동 속도나 행동을 결정하지 않음 |
| Graphics | 카메라 변환, 그리기, 그래픽 리소스 연동 | 점수나 충돌 결과를 판단하지 않음 |
| Physics | 충돌 후보 수집, 판정, 이벤트 전달 | 피격 대미지나 게임 종료를 결정하지 않음 |
| Audio | 재생, 정지, 음량, 오디오 라이브러리 연동 | 어느 상황에 어떤 소리를 낼지는 게임이 선택 |
| Assets | 로딩, 키 관리, 캐시, 해제 | 게임별 로드 목록과 실제 파일은 게임이 제공 |
| UI | 배치, 표시, 입력 전달의 공통 기능 | 체력·점수 등의 데이터는 게임이 제공 |
| Platform | 창, 포커스, OS 이벤트와 입력 수집 | 게임 코드에 OS 처리를 요구하지 않음 |
| Game/Sample | 씬 구성, 행동, 승패, 리소스 목록 | 엔진 서비스의 내부 메모리를 관리하지 않음 |
| Tools | 편집 입력, 파일 대화상자, 편집 데이터 | 게임 실행에 필수 의존성이 되지 않음 |

## 5. 객체 모델과 수명 규칙

기본 객체 모델은 Scene → GameObject → Component로 유지한다.
Layer는 표시 순서나 충돌 그룹 등의 분류 기능을 맡는다.
표시 순서와 충돌 필터가 서로 달라져야 하는 시점에 두 개념을 분리한다.

| 대상 | 소유자 | 다른 곳의 접근 방식 |
|---|---|---|
| Scene | SceneManager | 활성 씬 참조 |
| GameObject | Scene | 씬이 유효성을 보장하는 범위의 참조 |
| Component | GameObject | 해당 오브젝트가 살아 있는 동안의 참조 |
| Layer의 객체 목록 | 객체를 소유하지 않는 분류 목록 | Scene이 등록·제거를 관리 |
| Texture/AudioClip 등 | AssetStore | 정해진 리소스 수명 안에서 참조 |
| 창과 엔진 서비스 | Application 또는 실행 시작점 | 필요한 기능만 전달 |

C++에서는 소유 관계를 unique_ptr로 표현하는 것을 기본으로 한다.
객체 파괴 시 레이어 목록, 충돌 등록, 카메라 등의 참조도 함께 제거한다.
파괴된 객체를 가리킬 수 있는 장기 참조가 필요하면 조회 시 유효성을 확인하는 핸들을 검토한다.
리소스를 참조하는 씬과 객체를 먼저 정리한 다음 리소스를 해제한다.

### 5.1 컴포넌트 규칙

- Transform은 오브젝트마다 정확히 하나 존재한다.
- Script는 여러 개를 허용하는 것을 목표로 하되, 기존 사용 코드의 영향 범위를 확인하고 변경한다.
- 다른 컴포넌트의 중복 허용 여부는 타입별 정책으로 정한다.
- 중복이 금지된 컴포넌트를 추가하면 오류 또는 기존 인스턴스를 반환한다. 기존 컴포넌트를 암묵적으로 삭제하지 않는다.
- 초기화 전에 구성 요소를 추가하고 속성을 설정할 수 있어야 한다.
- 실행 중 컴포넌트 추가·제거는 별도 수명 정책이 정해지기 전까지 지원 범위에서 제외한다.

### 5.2 초기화와 활성화

생성자는 유효한 기본 상태를 만든다.
Initialize는 필요한 구성과 속성 설정이 끝난 뒤, 최초 업데이트 전에 한 번 실행한다.
씬에 다시 진입하는 동작은 OnEnter로 처리하고 Initialize를 반복하지 않는다.
일시 정지는 업데이트 대상에서 제외하는 상태 변경으로 처리한다.

씬 등록, 초기화, 활성화는 별도 동작으로 구분한다.
씬 구성 중에는 그 씬을 대상으로 객체를 생성하고, 전역 활성 씬을 임시로 바꾸지 않는다.

## 6. 프레임 및 씬 전환 규칙

아래 순서를 목표 규칙으로 삼는다. 기존 동작과 다른 부분은 단계적으로 옮기고 검증한다.

```text
1. OS 이벤트와 입력 수집
2. 시간 갱신
3. 활성 씬과 유지 객체의 Update
4. 물리/충돌 판정 및 이벤트 전달
5. LateUpdate: 충돌 결과 반영 후 카메라 등 최종 상태 조정
6. 렌더링
7. 삭제 요청 처리와 씬 전환 적용
```

오디오 서비스는 같은 프레임에서 발생한 재생 요청을 반영한 뒤 갱신한다.
첫 구조화 작업에서는 현재 시간 계산 방식을 유지한다.
프레임률에 따라 충돌이나 이동 결과가 달라지는 문제가 확인되면 고정 시간 간격의 물리 업데이트를 별도 단계로 도입한다.

요청 처리 규칙:

- 생성 요청은 다음 프레임 업데이트 시작 전까지 반영한다. 새 객체는 초기화 후 순회에 참여한다.
- 삭제 요청을 받은 객체는 이후 게임 업데이트와 렌더링 대상에서 제외하고, 실제 메모리는 프레임 끝에서 해제한다.
- 삭제된 객체를 대상으로 남아 있는 충돌 이벤트는 전달 전에 유효성을 확인하고 건너뛴다.
- 씬 전환 요청은 프레임 끝에 적용한다. 한 프레임의 전환 요청은 하나만 수락하고 중복 요청은 명시적으로 거절한다.
- 전환 시 이전 씬 종료, 충돌 상태 정리, 유지 객체 처리, 새 씬 준비, 진입 콜백 순서를 고정한다.
- 유지 객체는 단일 소유권을 유지하고 프레임당 한 번만 처리한다.

씬을 재사용할지 매번 다시 생성할지는 게임이 선택한다.
재시작은 명시적인 상태 초기화 또는 새 씬 생성으로 구현한다.

## 7. 공개 API의 기준

게임 개발자는 다음 의도를 엔진 내부 자료구조를 모르고 표현할 수 있어야 한다.

| 사용 의도 | API가 보장할 내용 |
|---|---|
| 씬 등록 | 등록만으로 활성 씬이 바뀌지 않음 |
| 씬 전환 요청 | 적용 시점과 실패 결과가 명확함 |
| 객체 생성 | 대상 씬이 명확하고 설정 후 초기화 가능 |
| 컴포넌트 추가 | 중복 정책과 초기화 시점이 명확함 |
| 객체 삭제 요청 | 즉시 삭제 여부와 이후 접근 범위가 명확함 |
| 입력 조회 | 게임 코드가 OS 포커스나 창 핸들을 직접 검사하지 않음 |
| 화면 크기 조회 | 읽기 전용 화면 정보로 접근 가능 |
| 리소스 로드/조회 | 실패와 키 중복 처리 정책이 명확함 |

인터페이스는 현재 구현 하나를 사용하는 얇은 경계부터 시작한다.
공통 객체 모델에서 HWND/HDC 같은 OS 타입을 제거하고, 필요한 실제 값은 플랫폼 및 그래픽 구현 내부에 둔다.
그리기 호출을 완전히 재설계할 필요가 없다면 RenderContext 같은 전달 객체로 경계를 먼저 만든다.
새 백엔드를 지원해야 할 때 해당 경계를 확장한다.

## 8. 구현 단계와 완료 기준

각 단계는 실행 가능한 상태로 마무리한다.
선행 단계의 완료 기준을 통과한 뒤 다음 단계에 착수한다.

| 단계 | 작업 | 산출물 | 완료 기준 |
|---|---|---|---|
| 0. 기준 확보 | 빌드와 샘플 실행 확인, 호출 흐름 기록, 기존 검사 실행 | 기준 실행 방법과 현재 의존 관계 | 기존 실패와 변경으로 생긴 실패를 구분할 수 있음 |
| 1. 엔진/게임 분리 | 엔진 전용 라이브러리 구성, 게임 코드와 리소스 등록 분리 | Engine + Sample 빌드 | Engine이 게임 헤더를 포함하지 않고 두 프로젝트가 빌드됨 |
| 2. 초기화 정리 | 생성/구성/초기화/활성화 분리, 중복 컴포넌트 정책 적용 | 수명 API와 초기화 규칙 | 초기화가 한 번 실행되고 씬 등록이 활성 씬을 바꾸지 않음 |
| 3. 소유권 정리 | 씬 소유권, 레이어 참조 목록, 삭제 요청 경계, 전환 정책 구현 | 소유 구조와 요청 처리 | 생성·삭제·씬 전환·유지 객체 이동에서 중복 처리와 잘못된 참조가 없음 |
| 4. 접근 경계 정리 | 전역 Application 접근 제거, 화면/입력 정보 전달, 플랫폼 타입 격리 | 공개 API와 연동 경계 | 기본 게임 코드가 창 핸들이나 엔진 내부 전역 변수에 의존하지 않음 |
| 5. 재사용 확인 | 새 샘플을 독립 실행 프로젝트로 구성, 문서에 따라 연결 | 두 번째 샘플과 사용 설명 | 엔진 구현 수정 없이 이동·충돌·씬 전환을 구현함 |

Tools 분리는 필수 단계의 회귀 검증 후 진행한다.
정적 매니저의 인스턴스 전환도 서비스별로 진행한다. 변경하는 서비스의 생성·종료 순서를 먼저 정한다.
큰 단계 안에서는 API 추가 → 사용 코드 이동 → 기존 API 제거 순서로 작은 변경을 만든다.
기능을 옮기는 변경과 동작을 바꾸는 변경을 분리하면 실패 원인을 좁히기 쉽다.

## 9. 검증 계획

| 검증 | 방법 | 확인 대상 |
|---|---|---|
| 빌드 경계 | 게임 코드가 없는 상태에서 Engine 빌드 | 게임 의존성 제거 |
| 초기화 | 초기화 호출 횟수와 첫 업데이트 시점 확인 | 이중 초기화, 구성 전 초기화 |
| 객체 삭제 | 업데이트/충돌 콜백에서 삭제 요청 | 순회 안정성, 남은 이벤트, 참조 해제 |
| 씬 전환 | 콜백에서 전환 요청, 중복 요청, 미등록 씬 요청 | 적용 시점, 오류 처리, 이전 씬 정리 |
| 유지 객체 | 씬 사이 이동 후 업데이트 횟수 확인 | 단일 소유권, 프레임 중복 처리 |
| 컴포넌트 | 중복 금지 타입 추가와 여러 스크립트 사용 | 정책 준수, 기존 객체의 암묵적 삭제 방지 |
| 리소스 | 누락 파일, 중복 키, 종료 순서 확인 | 오류 반환, 캐시 일관성, 참조 수명 |
| 회귀 | 기존 샘플의 이동·충돌·렌더링 실행 | 기존 동작 유지 또는 명시한 변경 |
| 재사용 | 두 번째 샘플을 문서만으로 연결 | API와 설명의 충분성 |

객체 수명과 상태 전환은 자동화된 검사로 확인한다.
화면, 입력, 오디오 연동은 짧은 실행 시나리오로 확인한다.
기존 충돌 검사는 관련 구조를 변경할 때 재사용한다.
폴더 이동만 검증하는 테스트나 구현을 그대로 반복하는 테스트는 추가하지 않는다.

## 10. 효율적으로 진행하는 운영 규칙

1. 한 변경에서 하나의 설계 문제를 해결한다.
2. 작업 전에 변경 목적, 영향 파일, 완료 기준을 적는다.
3. 작은 변경이 끝나면 해당 검증을 실행하고 실행 가능한 상태를 저장한다.
4. 실패하면 직전에 바뀐 경계를 먼저 확인한다.
5. 호환 API를 임시로 두었다면 제거할 단계와 조건을 기록한다.
6. 성능 변경은 느린 구간을 측정한 뒤 진행한다.
7. 추상화는 반복되는 요구나 명확한 교체 필요를 근거로 추가한다.

작업 기록 양식:

```text
문제: 현재 어떤 동작이나 의존성이 변경을 어렵게 하는가?
선택: 어떤 규칙으로 바꾸는가?
근거: 이 규칙이 실제 사용 사례를 어떻게 해결하는가?
영향: 어떤 API와 사용 코드가 바뀌는가?
검증: 어떤 관찰 결과로 완료를 판단하는가?
후속: 이번 변경에 포함하지 않은 일은 무엇인가?
```

## 11. 다른 프로젝트에 적용하는 방법

새 프로젝트에서는 이름과 폴더를 복제하기 전에 다음 항목을 먼저 작성한다.

1. 프로그램을 사용하는 주체와 가장 작은 실행 예제.
2. 변하지 않는 공통 기능과 사용 사례별로 달라지는 기능.
3. 객체와 서비스별 소유자, 생성 시점, 종료 시점.
4. 실행 한 주기의 처리 순서와 상태 변경 적용 시점.
5. 모듈별 입력, 출력, 의존 대상, 오류 처리 정책.
6. 공통 코드 변경 없이 두 번째 사용 사례를 만들 수 있는지 확인하는 시나리오.

예를 들어 게임의 Scene/GameObject는 다른 프로그램의 문서/항목이나 작업/작업 단계로 대응할 수 있다.
구체적인 객체 이름과 프레임 루프는 프로그램에 맞게 바꾸되, 책임·소유권·의존 방향·변경 경계·검증 기준은 같은 질문으로 설계한다.

## 부록 A. 현재 opEngine에 적용할 출발점

현재 코드를 확인한 결과에 따른 적용 항목이다. 다른 프로젝트에서는 이 부록을 자신의 구조에 맞게 교체한다.

| 현재 위치/동작 | 적용 작업 | 연결 단계 |
|---|---|---|
| opEngine_SOURCE 공유 소스가 opEngine_Window 정적 라이브러리에 포함됨 | 엔진 전용 빌드 프로젝트를 만들고 게임 라이브러리/실행 코드가 참조하도록 변경 | 1 |
| Editor_Window/main.cpp가 창과 엔진을 시작함 | 첫 Sample 실행 시작점으로 활용하고, 편집 도구 실행은 이후 분리 | 1, 후속 Tools |
| 엔진 LayerType에 Animal/Player/Brick 등 게임 분류가 있음 | 엔진은 범용 레이어 식별자를 제공하고 게임이 분류를 정의 | 1 |
| UIHUD가 HPBAR 리소스를 직접 찾음 | 공통 UI가 표시할 리소스와 데이터를 게임에서 전달받도록 변경 | 1 |
| SceneManager::CreateScene이 활성 씬을 변경함 | 등록/구성/활성화를 분리하고 대상 씬을 명시해 객체 생성 | 2 |
| AddComponent와 GameObject::Initialize 양쪽에 초기화 호출이 있음 | 초기화 진입점을 하나로 정하고 첫 업데이트 전 한 번 호출 | 2 |
| ComponentType별 슬롯 하나를 사용함 | 중복 추가 정책을 명시하고 스크립트 여러 개 지원 여부를 구현에 반영 | 2 |
| Layer가 GameObject를 삭제함 | Scene 소유 구조와 Layer 참조 목록으로 변경 | 3 |
| 씬 전환 중 즉시 활성 씬이 바뀜 | 프레임 경계에서 전환을 적용하고 충돌 이벤트와 참조를 정리 | 3 |
| 입력/카메라/텍스처가 extern application을 사용함 | 창·화면·그래픽 정보 접근을 서비스별 경계로 이동 | 4 |
| 컴포넌트와 씬 렌더링 API가 HDC를 전달받음 | 그래픽 전달 객체를 통해 OS 타입의 노출 범위를 축소 | 4 |
| Tests/CollisionTests.cpp와 RunTests.ps1이 있음 | 기존 검사를 기준으로 활용하고 수명/전환 관련 검증을 보강 | 0~5 |

현재 호출 순서는 Update → LateUpdate → 충돌 처리 → Render → 삭제 처리다.
본 문서의 목표 순서로 옮길 때는 충돌 이후 LateUpdate가 실행되도록 바뀌는 영향을 별도로 확인한다.
기존 예제의 화면과 조작을 기준 실행으로 남기고, 정해진 단계에 해당하는 변경만 적용한다.

## 부록 B. 최종 완료 체크

- [ ] 엔진은 게임 프로젝트의 헤더, 클래스, 리소스 키를 직접 참조하지 않는다.
- [ ] 객체와 서비스별 소유자 및 종료 순서를 문서로 설명할 수 있다.
- [ ] 초기화는 첫 업데이트 전에 한 번 실행된다.
- [ ] 생성, 삭제, 씬 전환의 적용 시점이 명확하다.
- [ ] 씬 전환과 유지 객체 처리에서 중복 삭제·중복 업데이트가 발생하지 않는다.
- [ ] 게임 코드의 기본 입력과 화면 정보 조회에 OS 핸들이 필요하지 않다.
- [ ] 기존 예제와 변경 영역에 대한 검증이 통과한다.
- [ ] 새 샘플을 연결하는 데 엔진 구현 수정이 필요하지 않다.
- [ ] 공개 API의 사용 방법과 실패 처리 방법이 문서에 있다.
- [ ] 각 주요 설계 선택의 이유와 검증 결과가 작업 기록에 남아 있다.
